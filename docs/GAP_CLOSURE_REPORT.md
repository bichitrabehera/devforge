## 2a. IdP authentication hardening (reported blocker closed)

The reported issue was reproduced before the fix: a fresh device proof was
redeemed, then the **same proof** with only `ttl_s: 120` and
`clock_skew: 86400` added returned a second token with `iat` exactly
86,400 s in the future, and `tokens.verify()` returned no error.

Fixes in `src/tokens.py` and `services/idp_server.py`:

- `tokens.device_proof_core()` defines the exact signed fields
  (`identity`, `device`, `ts`). The IdP consumed-proof ledger now hashes
  those fields **plus the signature**, not the whole request body. Changing
  unsigned fields can no longer create a new replay identity.
- The IdP no longer passes client-supplied `clock_skew` to issuance. All
  `iat`/`exp` values use the IdP's real clock. Non-finite `ttl_s` falls back
  to the 60 s default; the 3,600 s server cap remains.
- `tokens.verify()` now rejects an `iat` more than `MAX_IAT_FUTURE_S = 60 s`
  ahead of the verifier's real clock with `token_not_yet_valid`.
  This protects all verifiers (registry, nodes, messaging endpoint) even
  against a token minted by a misconfigured issuer.

After the fix, the same reproduction returns `proof_replayed`; a skew request
produces a token with `iat ≈ now`; and a deliberately future-dated token is
rejected at a node. Regression assertions live in
`tests/test_networked.py::test_07_control_plane_and_session_auth` steps
3c-2 and 3e.

## 3. Gap 1 — real lost-device re-enrolment

### Implemented flow

1. `user-blair` registers `device-blair` with a runtime-generated ML-DSA key.
   The recovery identity `recovery-user-blair` is registered separately with
   its **own** runtime-generated ML-DSA key. The organizer-approved public
   mapping is `RECOVERY_OF = {"user-blair": "recovery-user-blair"}`.
2. The device is revoked first with `user-blair`'s current token. The demo
   proves all three nodes deny it (`revoked_node-a`, `revoked_node-b`,
   `revoked_node-c`) before recovery is attempted.
3. The IdP `/recover/provision` endpoint requires a valid signed token whose
   subject is the bound recovery identity (or an organizer admin). It
   generates a fresh ML-DSA keypair service-side (“mock HSM”; identities file
   mode `0600`) and returns only a runtime-generated random
   `enrolment_secret`. Only its SHA-256 digest is persisted. No `dsa_sk`,
   `kem_sk`, private key, or digest appears in the response or logs.
4. The registry `/re_enroll` endpoint independently authorizes the recovery
   identity, keeps the old device revoked, registers a distinct replacement
   device, bumps the epoch, and journals/audits both `revoke` and
   `recovery_enrol`. There is no un-revoke path in this prototype.
5. The replacement obtains a token with the enrolment credential and accesses
   only its own authorized data. The lost key cannot mint a new token, and
   the old device/token/session remains denied at all nodes.

### Rejections observed in the final demo

| Attempt | Result |
|---|---|
| `/recover/provision` with another user's token | `reason = not_permitted` (`foreign_token_cannot_provision`) |
| `/recover/provision` with no token | `status = error` (`unauthenticated_provision_rejected`) |
| `/re_enroll` with an ordinary user token | `reason = not_permitted` (`wrong_token_cannot_re_enroll`) |
| Lost key presented to IdP `/token` | `status = error` (`lost_key_cannot_mint_token`) |
| Old device after recovery, node-a / node-b / node-c | `deny`, `reason = revoked` |
| Old device after real restart, node-a / node-b / node-c | `deny`, `reason = revoked` |
| Revoked recipient relayed through the nodes | final node `deny`, `reason = recipient_revoked`; endpoint never received plaintext |

Focused regression tests also prove rejection of a proof signed by an
attacker key, rejection when the recovery identity is not bound, rejection
when the bound identity is impersonated, invalidation of the old resumption
secret, distinct runtime-generated replacement keys, and that other users
retain access (`tests/test_gap_closure.py`).

## 4. Gap 2 — real node-to-node message delivery

Final measured route (`docs/demo_networked_output.json`):

```
user-alex → node-a → node-b → node-c → node-c/messaging-endpoint → user-blair
```

Every relay hop returned `decision = allow` with checks
`token, identity, device, revocation, key_version, permission`. The final
node verified recipient state before handing the envelope to the endpoint.
Checks passed:

- `relayed_delivered_through_ABC` and `endpoint_received_plaintext`.
- Reordering: arrival sequence `[1, 3, 2]`; counter `3` was buffered, counter
  `2` released `["second", "third"]` in order
  (`gap_buffered_at_endpoint`).
- Replay → `duplicate_replay`.
- Wrong recipient → `recipient_binding_mismatch`.
- Unknown recipient → denied at origin as `recipient_not_active`.
- Tampered and truncated ciphertext → `authentication_failed`.
- Wrong authenticated context → `context_mismatch`.
- Delivery failures were recorded with `msg_id`, `counter`, and `failure`.
- Revoked sender (`user-carol`) was denied at the origin node only, with
  `reason = revoked`; no plaintext reached the endpoint.

AEAD AAD now binds `sid`, `sender`, `recipient`, `counter`, `msg_id`,
`context`, and `key_version`. `CONTEXT = "track4-msg-v2"` is shared by the
embedded adapter and the socket transport. Revocation of the recipient is
enforced at the final/recipient node; every hop still enforces the sender.

## 5. Gap 3 — revocation persistence after a real restart

The demo sends `SIGKILL` to the registry process, waits for it to exit, and
restarts it as a new OS process. **No re-enrolment occurs before the restart.**
After restart:

- `registry_recovered_after_kill` and `committed_key_version_after_restart`
  passed; the active key version was preserved.
- `revocations_survive_crash` passed: `device-blair` was still in the policy's
  revoked set.
- `protected_data_after_restart` passed: `report.txt` still returned
  `Q3 numbers are green`.
- `revoked_after_restart_node-a`, `revoked_after_restart_node-b`, and
  `revoked_after_restart_node-c` all passed with `reason = revoked`.
- `revoked_recipient_after_restart` passed with `reason = recipient_revoked`.
- Only after these checks did the legitimate recovery flow run. It succeeded,
  and the old device remained denied on all nodes.

`tests/test_gap_closure.py::RealProcessRestartTest` repeats this with a real
`SIGKILL`, then performs legitimate recovery only after the restart and
confirms the replacement works while the old token is still denied.

## 6. Gap 4 — forward-secrecy demonstration

`tests/test_qa_gapfill.py::TestForwardSecrecyCompromise` performs an explicit
demonstration, not a formal proof:

1. Establish an ephemeral ML-KEM session and capture two ciphertexts plus the
   KEM encapsulation.
2. Close the session; assert the session key and ephemeral secret are
   `None` and `key_zeroized = true`.
3. Dump all persisted long-term secrets available in `state.json` (service
   DSA key, identity KEM/DSA secrets, and historical key versions).
4. Try every recovered long-term secret to decapsulate the captured KEM
   ciphertext and decrypt every captured message. None succeed
   (`assertFalse(broke)`).
5. Establish a **new** session after the compromise and deliver a fresh
   message successfully, confirming availability is not broken.

This demonstrates that captured traffic does not depend on the long-term keys
present in persisted state at the time of compromise. It is not a formal
cryptographic proof and does not cover capture before key deletion or
endpoint compromise.

## 10. Honest limitations

- The previously reported proof-replay/future-`iat` blocker is closed in the
  tested flows; no other known authentication blocker remains in this
  prototype. This is not a formal security audit or a "perfect" guarantee.
- The consumed-proof ledger is still in RAM, so an IdP process restart clears
  it. Proof freshness is 60 s and can no longer be extended by unsigned
  request fields, so the residual replay window is bounded by that freshness
  window plus a restart. A production IdP should persist consumed-proof
  digests.
- The IdP “mock HSM” is service-held key material in a `0600` local file; it
  is not a production HSM. A real deployment needs a real HSM/KMS, operator
  policy, and recovery approval workflow.
- Recovery trusts the organizer-configured `RECOVERY_OF` mapping and the
  recovery identity's ML-DSA key. It is not a proof of human identity.
- The replacement device authenticates with a random enrolment credential
  whose digest is stored by the service. This demonstrates loss recovery,
  not a full device-binding protocol.
- Forward secrecy is demonstrated against later exposure of persisted
  long-term keys; it is not a formal proof and does not cover live endpoint
  compromise or capture before ephemeral-secret deletion.
- Detector metrics are limited to the supplied synthetic practice set and do
  not predict production detection rates.
- The 69-check demo and all timing values are local, single-run evidence on
  one machine. They are not availability guarantees or worst-case bounds.
- All changes remain uncommitted and unpushed in this working tree.
